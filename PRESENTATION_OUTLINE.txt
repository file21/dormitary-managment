│                      [ 01:00 - 03:00 ]                                     │
└────────────────────────────────────────────────────────────────────────────┘

  ➤ "Let's start with ENCAPSULATION - the first OOP principle."
  
  ➤ Action: Open model/User.java
  
  ➤ Point to these lines:
     ```java
     private final String username;           ← Private!
     private final String passwordHash;       ← Private!
     private final Role role;                 ← Private!
     private final boolean active;            ← Private!
     
     public String username() { return username; }           ← Getter only
     public String passwordHash() { return passwordHash; }   ← Getter only
     ```
  
  ➤ Say: "Look at the fields - they're all PRIVATE. That means code outside
           this class CANNOT access them directly. They can only READ them
           through these getter methods. Notice - there are NO SETTERS.
           
           Why is this important? Because if someone sets username to null,
           the object is broken. By keeping fields private and providing
           controlled access, we prevent invalid states.
           
           This is ENCAPSULATION - hiding your data and controlling access."
  
  ➤ Show Bed.java for another example of immutability
  
  ➤ Transition: "Now, all these user types (Student, Admin, Proctor) share
                  common properties. We could copy this code three times...
                  but that's bad. Instead, we use INHERITANCE."

     ```java
     // User.java - Parent class

     public class Admin extends User { ... }
     
     // Proctor.java - Child class
     public class Proctor extends User { ... }
     ```
  
  ➤ Say: "See how Student, Admin, and Proctor all EXTEND User?

           username, passwordHash, role, active status, created time.
           
           Student also has its own properties: fullName, aauId, department.
           
           Why is this good? Because we defined username and password ONCE,
           in the User class. Not three times. No duplication.
           
           This is INHERITANCE - sharing common behavior through hierarchy."

  ➤ "Now let's look at ABSTRACTION - hiding complexity behind interfaces."
  
  ➤ Action: Open service/ScoringPolicy.java
  
  ➤ Show:
     ```java
     public interface ScoringPolicy {
         int score(Student student, DormApplication app);
     }
     ```
  
  ➤ Say: "This is an interface. It doesn't SAY HOW to calculate a score.
           It just says: 'You give me a student and application, I'll give
           you an integer score back.'
           
           The HOW is hidden. Different implementations can calculate
           differently. Let me show you."
  
  ➤ Action: Open service/DefaultScoringPolicy.java
  
  ➤ Point to implementation:
     ```java
     public class DefaultScoringPolicy implements ScoringPolicy {
         @Override
         public int score(Student student, DormApplication app) {
             // Complex calculation hidden here
             return baseScore + bonuses;
         }
     }
     ```
  
  ➤ Say: "One implementation. But you could create another that scores
           differently - a SpecialScoringPolicy for disabled students, for
           example. All they need to do is implement the same interface.
           
           This is POLYMORPHISM - many forms of the same interface.
           And it's ABSTRACTION - the complexity is hidden."
  
  ➤ Transition: "The real benefit comes when you look at the service layer.

┌────────────────────────────────────────────────────────────────────────────┐
│            SOLID PRINCIPLES - CODE ORGANIZATION (2 minutes)                │
│                      [ 07:00 - 09:00 ]                                     │
└────────────────────────────────────────────────────────────────────────────┘

  ➤ "Now let's look at how we organize these classes - SOLID principles."
  
  ➤ Action: Open service/ProctorService.java
  
  ➤ Show the constructor and fields:
     ```java
     public class ProctorService {
         private final ApplicationDao applicationDao;
         private final AllocationDao allocationDao;
         private final NotificationService notificationService;
         
         public ProctorService(ApplicationDao applicationDao,
                              AllocationDao allocationDao,
                              NotificationService notificationService) {
             this.applicationDao = applicationDao;
             this.allocationDao = allocationDao;
             this.notificationService = notificationService;
         }
     }
     ```
  
  ➤ Say: "Notice three things here:
     
     1. SINGLE RESPONSIBILITY (S in SOLID)
        This class ONLY handles check-in and check-out operations.
        It doesn't handle authentication, notifications, or anything else.
        One class = one job = easy to modify.
     
     2. DEPENDENCY INVERSION (D in SOLID)
        It receives INTERFACES as dependencies: ApplicationDao,
        AllocationDao, NotificationService.
        NOT concrete classes like ApplicationDaoPg.
        
        Why? Because if we later switch from MySQL to PostgreSQL,
        we just pass a different implementation. The service code
        NEVER changes.
     
     3. ENCAPSULATION
        The dependencies are private final - can't be changed from outside."
  
  ➤ Show the checkIn method:
     ```java
     public void checkIn(long applicationId, long bedId, String roomNumber) {
         DormApplication a = applicationDao.getById(applicationId);
         if (a.status() != ApplicationStatus.ACCEPTED) {
             throw new IllegalStateException("...");
         }
         allocationDao.allocate(applicationId, bedId, proctorUserId, roomNumber);
         applicationDao.setStatus(applicationId, ApplicationStatus.CHECKED_IN);
         notificationService.notifyUser(a.studentUserId(), "Checked in", "...");
     }
     ```
  
  ➤ Say: "Look at the clean separation:
           - Get data (using DAO interface)
           - Validate business rule
           - Update allocations (using DAO interface)
           - Send notification (using service interface)
     
           Notice it uses interfaces for ALL external dependencies.
           This makes it loosely coupled and testable."
  
  ➤ Transition: "This is professional-grade code design. Now let's see it
                  actually work in the application."

  "To summarize:
  
   • ENCAPSULATION keeps your data safe with private fields
   • INHERITANCE avoids code duplication through hierarchy
   • ABSTRACTION hides complexity behind interfaces
   • POLYMORPHISM makes code flexible and extensible
   • SOLID principles organize code into clean, maintainable packages
   
   This design means:
   - Easy to understand ("Where do I go to change X?")
   - Easy to modify ("Can change one thing without breaking everything else")
   - Easy to extend ("Just add a new class implementing the interface")
   - Easy to test ("Can use mock objects instead of real database")
   
   These aren't optional design patterns - they're industry standard practices
   for professional software development. Learning them now gives you a huge
   advantage in your career."
